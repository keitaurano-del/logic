# ロジカルライティング採点ルーブリック

作成: 2026-06-06
担当: content-creator（編 詠子）
対象: `POST /api/writing-score` — Claude API system prompt の設計根拠

---

## 概要

本文書は Logic アプリのロジカルライティング即採点エージェントが使用する採点基準の定義書です。
採点は PREP フレームワーク（Point=主張、Reason=理由、Example=具体例、Point 再提示=結論）を軸に
3 軸 + 総合スコアで構成され、`ScoringResult` 型のスキーマに対応しています。

```
scores: { point: 0-5, reason: 0-5, example: 0-5, overall: 0-100 }
comments / strengths / improvements: { ja: string, en: string }
```

---

## セクション 1: 各軸の詳細採点基準（5段階）

### 1-A. Point（主張の明確さ）— 0〜5点

BLUF（Bottom Line Up Front）の原則に従い、文章の冒頭 1〜2 文で結論・主張が明示されているかを評価します。
「何を言いたいか」が冒頭に来ているかどうかだけを見ます。内容の正誤は問いません。

| 点数 | 判定基準 |
|------|----------|
| **5点** | 冒頭の 1 文目（遅くとも 2 文目）に、具体的な主張・結論・依頼が明確に述べられている。主語と述語が明確で、一文で端的にまとまっている。 |
| **4点** | 冒頭に主張はあるが、やや回りくどい表現や前置きが 1〜2 語ある。ただし読み手は 1〜2 文で主張を把握できる。 |
| **3点** | 主張は存在するが、冒頭ではなく 3〜4 文目以降に置かれている。または冒頭に主張らしき文があるが抽象度が高く、「何を求めているか」が一読では分かりにくい。 |
| **2点** | 主張が文章の後半（後ろ半分以降）に現れる、または「〜についてお伝えします」のような話題提示だけで実際の主張が書かれていない。 |
| **1点** | 文章全体に目を通せば主張・意図は推測できるが、明文化されていない。読み手が行間を読む必要がある。 |
| **0点** | 主張・結論・依頼が一切明示されていない。何を言いたいのか文章全体を読んでも不明。 |

具体的な指標例（Point 軸）:
- 「今週金曜の会議を来週月曜に変更してください」→ 5点（依頼が 1 文目で完結）
- 「〇〇の件についてご連絡差し上げます。先日の状況を踏まえ、△△です」→ 3点（主張が 2〜3 文目にずれる）
- 「お世話になっております。先日はありがとうございました。〜（4文続いた後）〜変更をお願いしたく思います」→ 1〜2点（主張が末尾近く）

---

### 1-B. Reason（理由・根拠の論理性）— 0〜5点

主張に「なぜ」が紐づいているか、理由と主張の間に因果関係があるかを評価します。
理由の内容が事実かどうかは問わず、論理的な接続があるかだけを見ます。

| 点数 | 判定基準 |
|------|----------|
| **5点** | 主張に対する理由が 1 つ以上明示されており、主張と理由の間に「だから（因果）」の関係が成立している。理由が主張を支える構造になっている。 |
| **4点** | 理由は示されているが、因果が一部弱い（「〜なので」という接続があるが、論理的飛躍が小さくある）。全体として理由として機能している。 |
| **3点** | 理由らしき記述はあるが、主張との因果が明示されておらず、読み手が補完する必要がある。または理由が主張と無関係に並列されている。 |
| **2点** | 理由の記述が極めて薄い（「〜だから」の 1 語で終わる、または「〜と思います」程度）。因果として機能するには説明不足。 |
| **1点** | 理由に相当する文がなく、感想・状況の説明・事実羅列だけで構成されている。 |
| **0点** | 理由・根拠が一切ない。主張の裏付けゼロ。 |

具体的な指標例（Reason 軸）:
- 「来客対応が重なるためです」→ 因果として機能する（3〜5点範囲内で他要素と合わせて評価）
- 「先方の都合もありまして、色々と考えまして」→ 2点（理由の形はあるが内容が空洞）
- 「ご確認をお願いします」だけ → 0点（理由なし）

---

### 1-C. Example（具体例・データの適切さ）— 0〜5点

抽象的な主張が具体例・数値・事実で裏付けられているかを評価します。
例示がトピックに関連しているか、説得力を補強しているかを見ます。

| 点数 | 判定基準 |
|------|----------|
| **5点** | 具体例・数値・事例が 1 つ以上あり、主張または理由を直接補強している。例示がトピックと明確に関連している。 |
| **4点** | 具体例はあるが、やや抽象的（「たとえば昨日のミーティングで〜」程度）。または数値のみで文脈説明がない、もしくは文脈説明のみで数値がない。 |
| **3点** | 具体例と呼べる記述はあるが、主張・理由への貢献が限定的。「先日のような状況」など示唆にとどまる。 |
| **2点** | 具体例の形をしているが、主張・理由との関連が薄い（別の話題の例が混入している、など）。 |
| **1点** | 具体例と呼べるものは全くないが、文章全体を読めば何を指しているかは辛うじて推測できる（固有名詞・日時・固有の状況などが 1 語でも存在する）。 |
| **0点** | 文章全体が抽象的で、数値・事例・固有名詞が一切なく、具体性の手がかりがゼロ。 |

具体的な指標例（Example 軸）:
- 「先週の売上が 120 万円と前月比 15% 増加したため」→ 5点（数値で具体的に裏付け）
- 「実際に昨日確認したところ問題が見つかりました」→ 3点（具体的なエピソードはあるが内容が薄い）
- 「様々な要因があります」→ 0点（抽象のみ）

---

### 1-D. Overall（総合スコア）— 0〜100点

上記 3 軸の統合評価に加え、文章全体の論理的完成度を評価します。
一文の明確さ・接続詞の適切さ・抽象と具体の往復も加味します。

以下を目安に算出します:

| Overall レンジ | 状態 |
|----------------|------|
| **80〜100点** | 3 軸が概ね高水準（各 4〜5 点）。文章として完結しており、読み手の理解負荷が低い。PREP 全要素が揃っている。 |
| **60〜79点** | 3 軸のうち 2 軸が高水準（4〜5 点）で、1 軸が中程度（3 点前後）。文章として伝わるが改善余地がある。 |
| **40〜59点** | 3 軸が均等に中程度（各 3 点前後）、または 1 軸が高く 2 軸が低い。PREP の構成要素が一部欠けている。 |
| **20〜39点** | 3 軸のうち 1〜2 軸が低水準（各 1〜2 点）。構造が不完全だが、意図は読み取れる。 |
| **0〜19点** | 3 軸すべてが低水準（各 0〜1 点）。PREP の構造が著しく不足。 |

Overall に加味する要素（加減点の参考）:
- 接続詞の適切な使用（「そのため」「なぜなら」「たとえば」など論理関係が可視化されている）: +5点（1〜2 箇所）/ +10点（3 箇所以上、文章全体を通じて一貫して使われている）
- 文章末尾で主張への回帰がある（Point の再提示）: +5点
- 一文が 40〜60 字程度で読みやすく、一文一義が守られている: +5点
- 逆に一文が 80 字超で複数の述語が詰まっている: -5点

## セクション 2: 誤採点防止のガード原則

### 原則 1: 内容の正誤ではなく構造を評価する

採点対象は「PREP の構造が揃っているか」だけです。文章に含まれる主張の正しさ・事実の真偽・意見の妥当性は採点しません。

具体的な指示:
- 「この主張は根拠として弱い（事実としておかしい）」という判断で減点しない
- 「この例示は現実的でない」という理由で Example 点を下げない
- 論争的なテーマ（政治・ビジネス戦略・数値予測など）で、内容の立場に採点が引っ張られない
- 「内容が正しければ高得点、誤りなら低得点」の採点は禁止

例外なく適用します。採点コーチの役割は「論理構造のコーチ」であり「事実チェッカー」ではありません。

---

### 原則 2: 短い文章への不当減点禁止

2〜3 文の短い文章でも、構造が整っていれば適切なスコアを出します。

具体的な指示:
- 「文章が短すぎる」という理由だけで減点しない
- 2 文で Point + Reason が揃っていれば Point 4〜5 点・Reason 3〜4 点は出る
- 「もっと詳しく書いてほしい」という期待で Overall を下げない
- 文字数ではなく構造の充足度で判断する

ただし例示（Example）については、短い文章では必然的に具体例が省略されることが多く、Example 1〜2 点になるのは自然です。この場合 Overall 40〜55 点程度が妥当で、それは誤採点ではありません。

---

### 原則 3: 日本語・英語バイアスへの対応

日本語と英語を同じ基準で採点します。

具体的な指示:
- 日本語文はもともと結論を末尾に置く文化的傾向があります。これを理由に Point 点を自動的に下げない（PREP 構造を適用する課題として採点する）
- 英語文に対して「英語が下手だから」という理由で減点しない（文法・語彙の正確さは採点外）
- どちらの言語でも、採点軸は「構造（PREP）」のみです

---

### 原則 4: 「ケースバイケース」での採点回避禁止

各軸のスコアは必ず数字で出します。あいまいな答えは禁止です。

具体的な指示:
- 「この文章は状況によって評価が変わる」という理由でスコアをゼロのままにしない
- 「難しい判断です」「一概には言えません」で逃げず、現状の文章だけから採点する
- tool_use（`score_writing`）を必ず発火させ、すべての数値フィールドに値を入れる

---

### 原則 5: 加点主義（部分点を積極的に出す）

PREP の各要素が少しでも揃っていれば、その分の点数を出します。

具体的な指示:
- 「完璧ではないから 0 点」はしない。部分的に機能していれば 1〜2 点は出す
- 「主張はあるが弱い」→ Point 0 点ではなく 2〜3 点
- 「理由の記述が短い」→ Reason 0 点ではなく 1〜2 点
- 「具体例が示唆にとどまる」→ Example 0 点ではなく 1〜2 点
- 3 軸すべてが 0〜1 点の場合は Overall 0〜19 点の範囲に収まるのが自然（Overall 定義表の最低帯）。ただし「全軸 0 点かつ採点不能」以外では Overall も 0 点にしない。部分的に機能していれば、Overall も相応の点数を出す

---

### 原則 6: 初学者が萎えないトーン

コメント・強み・改善点は、前向きで建設的な表現にします。

具体的な指示:
- 「構造が崩れています」「全体的に弱いです」で終わらない
- 改善点は「こうするともっと良くなります」「〜を加えるとスコアが伸びます」の形にする
- 強み（strengths）では、文章の中に少しでも良い点があれば必ず言及する
- 総評（comments）は「採点結果の説明」ではなく「次に書く時のヒント」として機能させる

## セクション 3: ja/en 採点サンプル（各 3 件）

### サンプル A: 良い文章（ビジネスメール——会議の変更依頼）

#### 日本語サンプル

> 今週金曜日の定例会議を来週月曜日に延期してください。理由は、金曜に重要な顧客訪問が入り、資料準備が間に合わないためです。先方との商談は売上 200 万円規模で、優先度が高く対応が必要です。ご理解のほどよろしくお願いします。

想定スコア:
- Point: 5（1文目で「延期してください」と依頼が明示）
- Reason: 5（「顧客訪問が入り準備が間に合わない」という因果関係が明確）
- Example: 4（「売上 200 万円規模」という数値が含まれている。ただし商談の詳細はやや薄い）
- Overall: 83

採点理由:
Point は BLUF の原則通り冒頭で依頼が明示されています。Reason は「来客があるから準備できない」という因果が 1 文で完結しています。Example は数値が出ており裏付けとして機能しています。末尾で「ご理解のほど」と着地しており全体としてまとまった構造です。

#### 英語サンプル

> Please reschedule Friday's team meeting to Monday next week. I have a critical client visit on Friday that requires full preparation, leaving no time for the meeting. The client deal is worth approximately 2 million yen, making it our top priority this week.

Expected scores:
- Point: 5 (Imperative request placed at the very first sentence)
- Reason: 5 (Clear causation: client visit → no preparation time → meeting conflict)
- Example: 4 (Specific figure "2 million yen" supports the claim)
- Overall: 85

Scoring rationale:
The message opens with a direct request (BLUF principle fully applied). The reason is stated with a clear cause-and-effect structure. A concrete figure reinforces the urgency. The final sentence wraps up by restating the priority, providing a complete PREP structure.

---

### サンプル B: 普通の文章（提案書——新サービス導入）

#### 日本語サンプル

> 弊社では、来月から新しい顧客管理ツールを導入することを検討しています。現在の管理体制では対応できない部分が増えてきており、改善が必要だと判断しました。既存ツールと比べてコスト面でも優れていると思われます。

想定スコア:
- Point: 3（「導入を検討しています」という主張はあるが、「何を決断してほしいか」が不明確）
- Reason: 3（「対応できない部分が増えてきた」は理由の形をしているが因果が薄い）
- Example: 2（「コスト面でも優れている」だけで数値・具体例がない）
- Overall: 52

採点理由:
提案の意図はあるが冒頭が「〜を検討しています」と弱い。依頼なのか報告なのか役割が曖昧です。理由は挙げられているが「対応できない部分」が具体的に何かが示されていません。「コスト面で優れている」は主張に留まり、数値や事例がなく Example の裏付けが弱いです。

#### 英語サンプル

> We are considering adopting a new CRM tool next month. Our current system has some limitations that are becoming harder to handle. We believe the new tool could improve our efficiency and may offer cost benefits as well.

Expected scores:
- Point: 3 (Intent is communicated but the request or decision is unclear)
- Reason: 3 (Mentions "limitations" but doesn't explain the cause-effect chain)
- Example: 2 (No specific data or examples to support the claim)
- Overall: 50

Scoring rationale:
The message communicates an intention but lacks a clear call to action. The reason is vague ("some limitations") without elaborating on what those limitations are. The efficiency and cost claims are stated without any supporting figures or case examples.

---

### サンプル C: 弱い文章（報告書——プロジェクト進捗）

#### 日本語サンプル

> お世話になっております。先日お伝えしておりましたプロジェクトについてご連絡させていただきます。現在は各チームで作業を進めており、色々と課題もありますが、引き続き頑張ってまいります。何かありましたらご連絡ください。

想定スコア:
- Point: 1（報告の意図はあるが「何を伝えたいのか」が読み取れない）
- Reason: 1（課題はあると書かれているが「なぜ報告するのか」「何を判断してほしいのか」の因果が全くない）
- Example: 1（「色々と課題があります」とあるが具体例ゼロ）
- Overall: 22

採点理由:
冒頭が挨拶文だけで主張がありません。「ご連絡させていただきます」は話題提示であり主張ではありません。理由も具体例も欠落しており、PREP の構造要素が全て不足しています。ただし「現在進行中」という状況は伝わるため全軸 0 点にはなりません。

#### 英語サンプル

> I hope this message finds you well. I wanted to reach out regarding our ongoing project. Things are progressing and the team is working hard. There are some challenges, but we will do our best going forward. Please feel free to contact me if needed.

Expected scores:
- Point: 1 (No clear statement of what is being communicated or requested)
- Reason: 1 (Mentions "challenges" but provides no causal explanation)
- Example: 1 (No specific details, data, or examples)
- Overall: 20

Scoring rationale:
The message opens with a greeting rather than a point. The phrase "I wanted to reach out" is a topic indicator, not a claim. There is no reason given for the communication and no concrete details provided. The PREP framework is almost entirely absent, though intent to communicate is discernible.

## セクション 4: Claude system prompt テンプレート

以下は `server/routes/writing-score.ts` の `SYSTEM_PROMPT` として使用できるテキストです。
現行の `SYSTEM_PROMPT` 定数と差し替えて使います。tool_use（`score_writing`）は既存スキーマのまま利用します。

---

```
あなたは Logic アプリのロジカルライティング採点コーチです。
ユーザーが提出した文章を PREP フレームワーク（Point=主張、Reason=理由、Example=具体例）で採点し、採点ツールを呼び出して結果を返します。

【役割の定義】
採点の対象は「文章の論理構造」だけです。主張の正誤・事実の真偽・意見の妥当性は一切採点しません。
「PREP の各要素が構造として揃っているか」だけを見てください。

【採点基準】
- Point（0〜5点）: 冒頭 1〜2 文で結論・主張・依頼が明示されているか。BLUF の原則通り冒頭に置かれているか。
- Reason（0〜5点）: 主張に「なぜ」が紐づいているか。主張と理由の間に因果関係があるか。
- Example（0〜5点）: 具体例・数値・事実で主張や理由が裏付けられているか。例示がトピックに関連しているか。
- Overall（0〜100点）: 3 軸の統合 + 接続詞の適切さ・一文の明確さ・末尾での Point 再提示も加味。

【採点の姿勢】
- 加点主義で採点する。部分的に機能していれば点数を出す。「完璧でないから 0 点」は禁止。
- 短い文章（2〜3 文）でも構造が整っていれば適切な点数を出す。文字数で減点しない。
- 「ケースバイケース」「状況による」での逃げは禁止。全フィールドに数値を入れる。
- 内容の正誤で採点しない。構造だけを評価する。
- 日本語の文章は結論を末尾に置く文化的傾向がある。この傾向だけを理由に Point 点を自動的に下げない。あくまで「PREP 構造として冒頭に主張があるか」だけを評価する。
- 英語の文法・語彙の正確さは採点対象外。構造のみを評価する。
- 改善点は「〜を加えるとスコアが伸びます」という前向きな表現で伝える。
- 初学者が萎えないよう、良かった点を必ず 1 つ以上見つけて伝える。
- 全軸が 0〜1 点の場合でも Overall は 10〜20 点台を目安にする。全要素が一切なく採点不能な場合だけ Overall 0 点に近い値が出る。「完璧でないから全体的に低くする」はしない。

採点結果は必ず score_writing ツールを呼び出して構造化して返してください。
```

---

### system prompt 設計の注意点（開発者向け）

- 上記 prompt は 500〜600 字程度に収めており、`cache_control: { type: 'ephemeral' }` でのキャッシュに適した長さです。
- Phase 2 の RAG 移行後は、この固定 prompt 末尾に `## 関連教材ルール（検索結果）` セクションを動的に追記します（固定部は ephemeral キャッシュ、動的部はキャッシュ対象外）。
- `comments.ja` / `comments.en` は 100〜200 字の総評、`strengths` / `improvements` は 50〜100 字で設計します（tool スキーマの description 設定済み）。
- 採点が FALLBACK_RESULT を返した場合（Claude API エラー時）はフロント側でユーザーに再試行を促す表示を出してください。
